# ORCA Nova v1.8 workspace and automatic resources

## Quick use

1. Open **Settings**, specify the ORCA executable and a working directory, and save.
2. In **Calculation**, select an XYZ and calculation/preset.
3. Leave **CPU/RAM automatic allocation** on and select the total logical CPU budget. The same preference follows the supported Auto modes in Calculation, Batch / Queue, and Triplet Geometry Transfer. Saving settings or starting a calculation persists the preference. Manual fields are not synchronized.
4. Examine the generated INP and use Preflight, then run the relevant single calculation or workflow. The preview is based on the resource detection snapshot; the backend recalculates the final allocation just before execution.
5. For parallel jobs, switch to Batch / Queue, import multiple XYZs, and select each job's preset. For an active compatible queue, explicitly check **append to existing queue**. Inspect the queue's wait reasons and reservations. Results folders are separate.
6. For Triplet Geometry Transfer, verify the reference and all target atom mappings, protonation, charges, constraints and geometry warnings before submission. Automatic resources do not change the chemical workflow or determine the electronic-state identity.

## Resource policy (initial v1.8 policy, not an ORCA performance guarantee)

- Windows detects logical CPUs and physical memory with the OS API. Auto mode reserves 20% of currently available RAM and at least 1 GiB for the system; the smaller resulting budget is used.
- The maximum number of automatic parallel jobs is four. The user's CPU selection is an overall upper limit, not a guarantee that all cores are used.
- Each Job reserves the greatest stage CPU requirement and the greatest stage `ceil(nprocs * MaxCore * 1.25)` MB estimate. This is not a hard wall on the actual ORCA/MPI process tree memory.
- Automatic requests use at least 512 MB/core (heuristic) and at most 16000 MB/core. They may start with fewer cores when available RAM is low. Manual mode is appropriate for calculations that require different memory settings.
- On each dispatch, eligible never-started Jobs are reallocated using the remaining CPU/RAM budget and current physical memory. Newly started jobs are counted conservatively even before their RSS grows. If CPU slots or memory are not available, pending jobs wait and show the reason.
- Running and prepared/retry Jobs are not resized or rewritten. Imported/edited INP can be submitted in an otherwise automatic Batch, but their resource directives remain fixed. Directly edited standalone INP is also excluded from Auto.
- Appending to an active auto Queue requires the same total CPU cap and resource mode. The CPU/RAM envelope is retained, and the automatic concurrency ceiling may increase within it (never beyond four). Manual append requires identical limits. No automatic resume of a paused Queue is implied.
- If automatic probing is unsupported/unavailable, the application does not invent RAM capacity. Manual mode is available. CPU monitor data is whole-PC system usage; on Windows hosts with more than 64 CPUs the CPU percentage is withheld rather than misrepresent a single processor group. Job reservations are not measured process-level usage.
- The single-calculation runner remains mutually exclusive with an active Batch Queue; use Batch for simultaneous independent jobs.

## Workspace and data preservation

- Five pages: Calculation, Batch / Queue, Results, Tools, Settings.
- Presets are searchable across categories; the Recommended view is the starting filter.
- Additional Outputs and Batch comparison are collapsed initially.
- A directly edited INP is not regenerated by navigating or changing another Auto CPU field.
- Queue filters operate on the view only; deleting terminal history or source registrations never deletes calculation output files.
- Settings inputs are not overwritten by polling while they contain unsaved edits. Config writes use a same-directory temporary file followed by replacement; failed writes do not intentionally replace the previous settings.
- Existing scientific validation (Charge/Multiplicity, geometry dependencies, Triplet mapping, internal GBW linkage) remains required.

## Validation and release gates

Automated tests use synthetic inputs and mock ORCA child processes. They cover CPU allocation arithmetic, RAM pressure and recovery, cross-mode resource controls, active append and unchanged running INPs, independent output folders, manual INP protection, settings persistence and rollback, and preserved Triplet workflow. Windows Portable packaging and the authenticated API are also checked in CI. The real licensed ORCA 6.x/MPI runtime, resource-usage behavior and numerical scientific results must be verified on a workstation before calling them validated. This branch is a candidate, not a published Stable release.
